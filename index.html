03

Arquitetura de dados

Entrada simples agora. Integração contínua quando o volume exigir.

Peso, material, custo, lote e recompensa obedecem ao mesmo contrato de dados. O canal muda; validação, rastreabilidade e idempotência permanecem.

Comparação de operação, controle e escala

Dimensão MVP · Agilidade controlada CSV / XLSX + formulário B2B Final · Escala conectada REST / Webhooks + ERP
Origem Upload de planilha formatada (.CSV ou Excel) pela marca ou cadastro manual simplificado no Dashboard B2B. API REST e Webhooks ligados ao SAP, Oracle ou ERP proprietário; sincronização automatizada por lote.
Contrato mínimo batch_code, serial, material, weight_g, unit_cost, reward Mesmo payload versionado + source_event_id + occurred_at + signature
Validação Prévia antes da importação, validação de colunas/tipos, rejeição linha a linha e relatório para correção. JSON Schema, assinatura do cliente, idempotência por evento e dead-letter queue para payloads inválidos.
Processamento AWS Upload assíncrono, staging no S3, worker de validação e gravação transacional no PostgreSQL. API Gateway → Lambda/NestJS → fila → consumidor idempotente → RDS, com retorno de status por Webhook.
Latência esperada Minutos por lote; adequado para carga inicial e reposições programadas do piloto. Segundos por evento; suporta produção contínua e múltiplas fábricas/tenants.
Auditoria Arquivo original, autor, timestamp, hash do upload e relatório de aceites/rejeições preservados. Correlation ID ponta a ponta, versão do contrato, trilha de retry e reconciliação diária com o ERP.
Responsável Operador autorizado da marca, com escopo restrito ao próprio tenant. Conta técnica do ERP com OAuth2 client credentials, segredo rotacionado e rate limit por tenant.

Gate 01

Template estabilizado

≥ 98% das linhas importadas sem intervenção em três lotes consecutivos.

Gate 02

Volume ou frequência excedidos

Mais de 100 mil embalagens/dia ou mais de uma carga operacional diária.

Decisão

Ativar integração ERP

O contrato de dados não muda; apenas o adaptador de entrada é substituído.

06

PostgreSQL + Prisma

Quatro entidades para sustentar o núcleo transacional.

O modelo privilegia unicidade, idempotência e consultas por tenant. Saldos são projeções rápidas; o histórico de transações continua sendo a fonte auditável.

prisma/schema.prisma 
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

enum PackagingStatus {
  GENERATED
  IN_CONDOMINIUM
  COLLECTED
  PROCESSED
}

enum RequestStatus {
  PENDING
  ASSIGNED
  COMPLETED
  CANCELLED
}

model Tenant {
  id                 String              @id @default(uuid()) @db.Uuid
  name               String
  slug               String              @unique
  subscriptionActive Boolean             @default(true)
  monthlyFeeCents    Int                 @default(25000) // €250.00 fixo
  createdAt          DateTime            @default(now())
  updatedAt          DateTime            @updatedAt
  packages           Packaging[]

  @@index([createdAt])
}

model Condominium {
  id                 String              @id @default(uuid()) @db.Uuid
  name               String
  slug               String              @unique
  address            String
  createdAt          DateTime            @default(now())
  updatedAt          DateTime            @updatedAt
  collectionRequests CollectionRequest[]
  packages           Packaging[]

  @@index([createdAt])
}

model Cooperative {
  id                 String              @id @default(uuid()) @db.Uuid
  name               String
  slug               String              @unique
  pixKey             String?
  createdAt          DateTime            @default(now())
  updatedAt          DateTime            @updatedAt
  collectionRequests CollectionRequest[]
  packages           Packaging[]

  @@index([createdAt])
}

model CollectionRequest {
  id             String            @id @default(uuid()) @db.Uuid
  condominiumId  String            @db.Uuid
  cooperativeId  String?           @db.Uuid
  status         RequestStatus     @default(PENDING)
  scheduledFor   DateTime?
  completedAt    DateTime?
  createdAt      DateTime          @default(now())
  updatedAt      DateTime          @updatedAt
  condominium    Condominium       @relation(fields: [condominiumId], references: [id], onDelete: Cascade)
  cooperative    Cooperative?      @relation(fields: [cooperativeId], references: [id], onDelete: SetNull)

  @@index([status, createdAt])
}

model Packaging {
  id                String             @id @default(uuid()) @db.Uuid
  tenantId          String             @db.Uuid
  condominiumId     String?            @db.Uuid
  cooperativeId     String?            @db.Uuid
  serial            String             @unique
  batchCode         String
  status            PackagingStatus    @default(GENERATED)
  material          String
  weightGrams       Decimal            @db.Decimal(10, 2)
  unitRewardCents   Int                // Valor pago p/ unidade
  externalQrHash    String             @unique @db.VarChar(64)
  internalQrHash    String             @unique @db.VarChar(64)
  createdAt         DateTime           @default(now())
  updatedAt         DateTime           @updatedAt
  tenant            Tenant             @relation(fields: [tenantId], references: [id], onDelete: Restrict)
  condominium       Condominium?       @relation(fields: [condominiumId], references: [id], onDelete: SetNull)
  cooperative       Cooperative?       @relation(fields: [cooperativeId], references: [id], onDelete: SetNull)

  @@index([tenantId, batchCode, status])
  @@index([status, updatedAt])
}

model AuditLedger {
  id             String            @id @default(uuid()) @db.Uuid
  prevHash       String            @db.VarChar(64)
  rowHash        String            @unique @db.VarChar(64)
  payload        Json
  signature      String
  createdAt      DateTime          @default(now())

  @@index([createdAt])
}

Invariantes de domínio

O banco impede o erro antes do código.

01

Scan único

internalQrHash @unique bloqueia uma segunda leitura ou duplo crédito para a mesma embalagem.

02

Idempotência de coleta

A vinculação transacional das coletas aos condomínios solicitantes e QRs únicos impede duplicidades de resgate nos apps.

03

Assinatura do Ledger

Cada transação alimenta a cadeia do ledger gerando um hash encadeado assinado com a chave da plataforma.

04

Consulta indexada

Índices compostos cobrem dashboard por tenant/lote/status e requisições por condomínio/cooperativa.

05

Isolamento de Tenant (Zero Leakage)

Toda consulta e escrita filtra estritamente por tenantId resolvido no middleware, isolando 100% os dados e métricas de cada fábrica.

Regra de transição

O status é controlado transacionalmente. Apenas GENERATED → IN_CONDOMINIUM → COLLECTED → PROCESSED é aceito.

Casos de teste e falhas

Cada risco possui gatilho reproduzível, contenção, recuperação e critério de aceite. Expanda uma linha para ver o teste de engenharia.

Crítico Alto Médio
ID Cenário Severidade Impacto real Controle de engenharia Detalhes
F-01

Fraude de Escaneamento

Tentativa de escanear QR Codes falsificados ou duplicados no condomínio.

 CRÍTICO Pagamento indevido de recompensas e desvio nos relatórios de impacto da marca. O app de coleta da Cooperativa valida a assinatura criptográfica do lote da Fábrica. Se inválido ou já escaneado, bloqueia o crédito imediatamente.

Entrada

QR Code escaneado com assinatura de lote inválida ou alterada.

Oráculo

Resposta INVALID_SIGNATURE; rejeitado localmente e logado no servidor.

Recuperação

Alerta de fraude enviado ao painel da cooperativa e da plataforma.

Aceite

100% de rejeição de assinaturas falsas; falso negativo = 0%.
F-02

App offline na Coleta

A cooperativa perde a conexão de rede na garagem ou depósito do condomínio.

 ALTO Impossibilidade de registrar coletas no ato, gerando atraso e erros manuais. Cache local em SQLite criptografado no app da cooperativa. As validações geram hash monotônico offline e são transmitidas ao retornar a rede.

Entrada

Rede desconectada durante leitura de 50 embalagens no condomínio.

Oráculo

Registros marcados como OFFLINE_VERIFIED com UUIDs vinculados localmente.

Recuperação

Sincronização em segundo plano envia dados em lote; API processa com idempotência.

Aceite

Zero perdas de registros após 12h offline; sincronização concluída com sucesso.
F-03

Fila de Matching Congestionada

Pico de solicitações de coletas simultâneas por condomínios.

 ALTO Atraso na atribuição das solicitações de coletas urgentes para as cooperativas. A fila de eventos do NestJS gerencia e distribui requisições de forma assíncrona, priorizando por volume acumulado e proximidade das cooperativas.

Entrada

Carga simulada de 5.000 requisições simultâneas de condomínios.

Oráculo

Requisições entram na fila MATCHING_QUEUE; latência de resposta do app < 200ms.

Recuperação

Trabalhadores da fila consomem mensagens em paralelo; balanceamento de coletas atualizado.

Aceite

Processamento de todas as atribuições em menos de 3 minutos, sem perda de pacotes.
F-04

QR Code Reutilizado

Tentativa de bipar o mesmo código interno mais de uma vez para obter recompensas.

 CRÍTICO Créditos de compensação inflados e distorção das métricas do lote auditado. O banco PostgreSQL impõe unicidade no campo `internalQrHash`. O status transita para `COLLECTED` e impede novos acionamentos.

Entrada

Requisição de bipagem com hash já marcado como COLLECTED no DB.

Oráculo

Lançamento de exceção de violação de restrição única SQL; transação revertida.

Recuperação

O app exibe erro de código inválido/duplicado e sinaliza o serial para inspeção.

Aceite

Nenhuma duplicação de crédito permitida sob concorrência intensa.
F-05

Planilha de Lote Inválida

Fábrica envia arquivo com dados corrompidos ou campos em branco.

 MÉDIO Problemas futuros na leitura do QR Code e falhas na integridade do banco. Validação com JSON Schema em nível de API B2B. O lote só é ativado no banco se passar em 100% dos testes de formato e regras.

Entrada

Upload de CSV com 5.000 itens contendo erros de formatação de hashes.

Oráculo

A pré-validação aborta a importação transacional e devolve relatório de erros.

Recuperação

O operador é alertado na tela para corrigir e reimportar o lote.

Aceite

Nenhum registro parcial inserido no banco de dados.
F-06

Falha no Cashout Cooperativa

API bancária ou provedor PIX/SEPA falha durante a liquidação de saldo da cooperativa.

 ALTO Erro de pagamento gerando desconfiança e bloqueio financeiro operacional. Reserva de saldo transacional, uso de chave de idempotência exclusiva no gateway e webhook de confirmação assíncrona.

Entrada

Requisição de saque com resposta de timeout HTTP da API de pagamento.

Oráculo

Status é mantido em PENDING; saldo reservado em conta transacional.

Recuperação

Fila de reconciliação de saldo consulta a transação via webhook ou polling.

Aceite

Garantia de transação única (payout exato), sem duplicidades de saques.
